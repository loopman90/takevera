# Takevera

Takevera is an open-source, offline-first desktop workspace for writing scripts and preparing small productions. Projects are stored as readable JSON files on the user's Mac. No account, subscription, AI provider, or network connection is needed for local writing and production planning.

## Snel beginnen / Quick start

1. **Installeren / Install:** Open het juiste Mac-installatiebestand en sleep Takevera naar **Programma’s**. Open it and drag Takevera to **Applications**.
2. **Beginnen / Start:** Open Takevera en kies **Nieuw project**. Open Takevera and choose **New project**.
3. **Schrijven / Write:** Open **Script**, voeg een scène toe en begin met schrijven. Wijzigingen worden automatisch lokaal opgeslagen. Open **Script**, add a scene and start writing; changes save locally.
4. **Productie / Production:** Gebruik **Productie** voor draaidagen, shotlists, apparatuur, licht en call sheets. Use **Production** for shoot days, shot lists, equipment, lighting and call sheets.
5. **Hulp / Help:** Kies **? Help mij** bovenaan de app voor uitleg bij het huidige scherm, stappenplannen en de volledige handleiding. Choose **? Help me** in the app for screen guidance, walkthroughs and the full guide.

Lees de [Nederlandse handleiding](USER_GUIDE_NL.md) of de [English user guide](USER_GUIDE_EN.md). De app werkt lokaal; AI en samenwerken zijn optioneel. This app works locally; AI and collaboration are optional. De lokale Mac-versies zijn niet door Apple genotariseerd; macOS kan een waarschuwing tonen.

## What is here

This repository started empty (no source files, README, or project-specific AGENTS.md). The app uses Electron and a browser-native interface: its renderer has no Node access, and a narrow preload API exposes selected project, asset, localization, and optional AI operations. This keeps the app portable to Windows and Linux without tying the project format to one operating system. The owner selected the MIT licence and confirmed the copyright notice. Third-party attribution still needs review before distribution.

### Phase 1 features implemented

- Create, open, search, rename, delete, import, and export projects; open the bilingual in-app glossary. New installations start without projects. The project wizard captures logline, synopsis, creators, production type, and language. Project interchange uses a documented JSON envelope; imported projects receive a new local ID. A separate full project folder backup stores a manifest and copies all available PNG/JPEG/WebP images into an `assets/` folder, with SHA-256 verification on import; choose it when the JSON bundle size limit is too small. PNG, JPEG, and WebP images attached to scenes, moodboards, and storyboards can be copied into project storage or linked at their original location. Linked files are checked and flagged when unavailable. JSON exports bundle available linked and copied images (up to 28 MB total); missing or unsupported files are reported and must be relinked or added again after import. Full project folder backups have no combined image-size cap; they support up to 100 images of at most 15 MB each and require the manifest and `assets/` folder to stay together.
- Local JSON project files and up to ten rotated automatic snapshots created on saves after a quiet interval.
- Script scenes with heading, action, character, dialogue, location, duration, notes, production-specific labels, editor, scene-card, and continuous-script views, and reorderable custom blocks for stage direction, narration, transitions, sound, music, or other text. Character/speaker and location fields suggest names already in the project while still accepting custom text. Find and replace across script blocks; add, duplicate, remove, approve, lock, and drag-reorder scenes; autosave and word/page/time estimates. Per-scene comments can quote selected text from a script field or custom block, jump back to that selection, and flag anchors whose text moved or changed. Comments are stored locally and synchronize when real-time collaboration is connected. The scene panel and navigation sidebar can be resized by dragging their dividers; the sidebar width is remembered and its divider also supports arrow, Home, and End keys. Import PDF text and import/export basic Fountain (`.fountain` / `.txt`), Final Draft XML (`.fdx`), and Word OpenXML (`.docx`) scripts. Before Fountain, FDX, or DOCX import, review the detected scene headings, script-block counts, and format-specific warnings; Takevera project attachments can be restored as new projects. Print scripts with a title page naming the production type, US Letter or A4 pagination, page numbers, configurable font and margins, automatic wrapping, revision-page colors, and a reference-image appendix. Film, documentary, commercial, and video scripts use screenplay dialogue indents; theatre prints centered act, scene, and character cues with italic stage directions; podcasts print centered speaker cues, full-width dialogue, and italic audio directions.
- Project bible with editable character history, traits, relationships and arcs; location addresses, access, parking, travel times, contact, safety and sound notes; story timeline, world rules, key objects, style guide, and project notes. Structured timeline events can include date/time, description, notes, and a linked scene; users can reorder events, and they are included in continuity AI context and as a formatted list in production-book output. Character and location entries link to matching scenes, which can be opened directly from the bible. Save dated script revision rounds with notes and page colors, compare any two saved revisions or compare one with the current script field by field, and restore previous versions. Marked scenes print on tinted pages; enable background graphics in the print dialog to retain color in the PDF. Undo and redo project edits during the current app session with Cmd/Ctrl+Z and Shift+Cmd/Ctrl+Z.
- Cast and crew roster with roles, shoot-day assignments, per-day availability checks, call times, personal notes with a separate call-sheet inclusion choice, and optional contact details. Project-bible locations also track availability per shoot day; schedule suggestions and the day overview flag unavailable or unconfirmed locations and scene locations without a matching project-bible entry. Personal phone numbers are included in a call sheet only when the per-person export checkbox is enabled.
- A shoot-day overview with multiple days, scene assignment, a reviewed location-grouping suggestion based on scene locations/headings (without assigning times or claiming availability), a dedicated print-friendly call sheet, editable timed schedule items with overlap and expected-wrap warnings, and a draft schedule that can group by location, cast, availability, production needs, or script order, asks for shoot-time estimates and a default inter-location travel time when a destination lacks its own estimate; numeric estimates saved on destination locations override the default, which may stay blank when every move has a specific estimate; inserts a timed break when configured, starts at the call time, and flags known or missing cast and location availability for review, missing call-time, contact, and location warnings, and editable safety, catering, weather contingency, lighting, and sound information. Call sheets and full-book exports require a confirmation before printing; a separate per-export switch controls contact and emergency details, and personal phone numbers also require per-person consent. Call sheets include scene-linked location addresses, access and parking instructions, travel time, safety notes, and sound rules from the project bible; location contacts appear only when contact export is enabled. The call sheet also surfaces production tasks and equipment assigned to that day, with status controls so on-set users can update progress in place. A focused on-set call-sheet mode provides large text, quick filtering, and shoot-day switching on small screens. Weather and daylight notes can be entered manually; after confirmation, Open-Meteo can provide a forecast plus astronomical sunrise, sunset, and daylight duration for a town/postcode and shoot date. The request requires confirmation, records the source and retrieval time, and does not run in the background. Approved shoot days can be locked; locking protects schedule details, scene assignments, and that day’s shot list until unlocked.
- A script scan that proposes character cues, locations, and explicit music/sound cues from structured scenes, marks new references as needing review, and records where each appears; per-scene production inventory for props, costumes, equipment, sound cues, make-up, effects, and transport, with owner and status tracking. Inventory categories offer translated suggestions and accept custom text; continuity, lighting, and sound notes are editable per scene, and lighting setups record each fixture, position, modifier, power need, and safety note per scene or shot. Shot cards include per-shot lighting notes and image references with source and usage-rights notes. The lighting and sound workspaces also store structured per-scene and per-shot setups: lighting fixtures, positions, modifiers, power needs, and safety notes; microphones, placement, recorder, recording format, ambience, wild tracks, and sound risks. Both workspaces store separate image references on each scene and shot, including captions, source, creator, date, usage rights, and notes; these references are checked for missing linked files, included in project bundles and shared snapshots, and printed in the matching plan reports and production book. In the lighting workspace, any project lighting reference can also be used as a floor-plan or mood-image backdrop; users can place, drag, keyboard-position, label, and annotate fixture markers, which print over the image. Production details are manually reviewed rather than silently presented as extracted facts.
- A shot list with scene, description, framing, movement, lens/equipment, sound, duration, and notes. Common shot, camera, lighting, sound, equipment-category, and crew-role values appear in a dropdown on editable text fields; the shot list’s lens/equipment suggestions also include gear already entered in the equipment list and scene breakdown. Storyboard framing, movement, and sound fields use the same suggestion lists as the shot list. Click a field or press the down arrow to open suggestions, then choose one or type a custom value. Equipment and scene-inventory forms suggest common gear names (such as cameras, microphones, and light stands) plus item names and owners already used in the project; task forms suggest common production tasks (such as confirming cast, arranging catering, and checking equipment) plus previously used task names and owners. Tasks can be assigned to one shoot day or all days; call sheets show tasks for their selected day. Removing a shoot day moves its tasks to all days, moves that day’s shots to the next day (or the previous day when removing the last one), and adjusts later assignments. These starter suggestions follow the selected interface language. New values can still be typed freely. The separate equipment list tracks item/category, quantity, owner, status, notes, and scene/shot assignments; it can be included in the production book and printed as its own report. Named production-book export templates can be saved per project; each controls which shoot-day and project sections appear and their order within those groups. Add project-specific custom text sections, then include, hide, and order them independently in each template. Moodboards, storyboards, and other reference images have independent template switches; scene, shot, character, location, lighting, and sound images are collected in the optional reference-image appendix.
- Separate print/PDF reports for the shot list, lighting plan, sound plan, cast/crew roster, and equipment list. Reports include relevant scene and shot references; cast/crew phone numbers appear only when both export-level and per-person consent are enabled.
- Separate named shortlists that select scenes, shots, script characters, cast/crew members, locations, and equipment; selection order is adjustable and is preserved in the production-book export.
- Production tasks with owners, due dates, and language-independent status keys; old Dutch and English status values remain readable after changing interface language.
- A project budget with editable cost categories, owners, estimated and actual amounts, currency selection, totals, and an optional budget section in the production-book export. Category and owner suggestions include common and previously used values, while custom text remains allowed.
- Project backup manager to list, restore, and delete automatic snapshots or recovery points; restoring keeps the replaced version as a recovery point.
- Multiple named moodboards per project with images, links that open only HTTP/HTTPS destinations, captions, source, creator, date, usage-rights notes, additional notes, text, and color swatches; print the active moodboard as a PDF; drag, resize, select, and group moodboard items; storyboard cards can link to scenes and shots and include frame images, visual direction, sound, duration, provenance, and notes. Cards can be duplicated and reordered and printed to PDF through the system dialog.
- Import PNG, JPEG, and WebP reference images by copying them into the local project asset folder or linking their original location; drag files onto scene, shot, character/location, moodboard, storyboard, lighting, and sound drop zones for the same consent prompt. Attach reference images to scenes, shots, characters, and locations with captions, source, creator, date, usage-rights notes, and additional notes; lighting and sound references can be attached separately to the project, individual scenes, and individual shots. All managed image references are included in project interchange bundles and shared snapshots, and scene- and shot-specific lighting/sound references appear in the corresponding standalone reports and production-book printouts. Production-book templates can include the project bible with character and location reference images.
- Dutch and English interface controls, independent project script-language field, built-in spelling suggestions in script fields using the project language, light/dark appearance, and project-wide search across script text, project bible, production data, and boards.
- Optional AI assistance through a user-configured OpenAI-compatible endpoint or local model server can explore ideas and loglines, develop synopsis and story structure, develop characters, rewrite scenes, review or summarize the full script, check continuity, translate, and propose production breakdowns. The assistant is available from both Script and Production; opening it from Production preselects the breakdown task. API keys are encrypted with Electron secure storage when available. Before each request, the app previews the selected context (scene, project overview, character bible, full script, or production data) and asks the user to authorize sending it. Full-script requests use at most the first 16,000 characters of context; the preview marks when it is truncated. Results are never applied automatically: users can keep them as separate project suggestions or, for scene tasks, add a separate suggestion block.
- A first-launch introduction that can be skipped. The project overview shows each project’s last-change date and time plus a progress bar derived from completed production tasks; projects without tasks explain how to start tracking progress.
- Print-friendly system dialog for the active script or production view and a complete multi-day or active-day production-book report with editable version and status; use the macOS print dialog's Save as PDF option.

### Known limitations

Equipment can be filtered by shoot day and status, with review notices for needed items, zero quantities, and possible duplicate names. Shot, lighting, and equipment presets are saved with the project and can be reused without carrying scene or day assignments. Matching names alone do not establish a booking conflict.

For a phase-by-phase comparison with the original specification, see [Specification coverage](docs/SPEC_COVERAGE.md).

See [Known limitations](#known-limitations) and [Realtime collaboration](#realtime-samenwerking-optioneel) below. The app does not claim Celtx compatibility. Scanned PDF OCR uses Apple Vision locally on macOS and requires Swift command-line tools; it is unavailable on Windows and Linux. On macOS, spelling uses the native system spellchecker and its available dictionaries. On Windows and Linux, Electron uses Hunspell dictionaries and may download a missing dictionary; the spellchecker itself does not upload typed text. The print layout supports per-project US Letter or A4 paper, a font family and 10–12 pt size, adjustable inner text margins, cue/dialogue/parenthetical indents, dialogue width, and line spacing. Page margins can be set per side from 0.25 to 2 inches; extra text margins are applied inside them. A selected print font must be installed or bundled; font metrics affect screenplay pagination. Courier Prime and Bebas Neue are bundled for offline use under their respective [Courier Prime](../src/fonts/courier-prime/OFL.txt) and [Bebas Neue](../src/fonts/bebas-neue/OFL.txt) SIL Open Font Licenses. Avenir Next uses the system installation with fallbacks. Printed revision-page colors depend on the print dialog’s background graphics setting.

## Run on macOS

1. Install Node.js 22.13 or newer, or Node.js 24 or newer (PDF.js requirement).
2. In this folder, run `npm install` (internet is only needed to obtain the development tools).
3. Run `npm start`.
4. For a local macOS DMG/ZIP build, run `npm run dist:mac`.

The packaged app requires macOS 13 Ventura or newer; both generated app bundles declare `LSMinimumSystemVersion` 13.0. Electron 44 and newer require macOS 13 or later. The macOS scripts create Apple Silicon (arm64) and Intel (x64) packages. The Apple Silicon app is built on this host. Intel packaging is available through `npm run dist:mac:x64`; Intel hardware runtime validation has not been performed. Windows and Linux release builds are deferred; their experimental portable archives are not tested releases. The local DMG and ZIP use an ad-hoc signature, which does not identify a developer and is not notarized. Open-source builds may be distributed without a paid Apple Developer account, but an ad-hoc signature does not establish the developer’s identity and macOS may block the app. Notarization and Developer ID signing are optional distribution choices, not substitutes for the required security and release checks. This repository does not include signing credentials or an automatic updater. Back up project files before installing a major app update.

## Install a macOS build

1. Choose the matching `Takevera-0.1.0-arm64.dmg` for Apple Silicon or `Takevera-0.1.0-x64.dmg` for Intel in the generated `dist/macos-*` folder.
2. Open the DMG and drag **Takevera** to **Applications**. Eject the mounted disk image when the copy finishes.
3. This repository build is ad-hoc signed and not notarized. macOS may block its first launch or show a security warning. No official release has been published. Follow the user guide and Apple’s security guidance for future unsigned releases; an ad-hoc signature does not prove the developer’s identity.
4. Before replacing an older app, export important projects and copy the project storage folder to a separate backup location. Project JSON and image files remain in the configured storage folder when the app is replaced.

There is no automatic update channel. Install updates manually after checking the release and preserving a backup.

The current macOS build is ad-hoc signed and not notarized. Developer ID signing and notarization are optional and not configured in this build. Never describe an unsigned or unnotarized build as signed by an identified developer or notarized.

Run `npm test` for production data checks. `npm run test:smoke` opens an isolated, hidden Electron window and uses a mock storage interface to check equipment filters, presets, lighting references, save/reopen, and call-sheet controls. `npm run test:storage` uses a temporary documents folder and the real application IPC handlers to check copied images, project export/import, call-sheet PDF generation, saving, backup recovery, and deletion. Both Electron checks need a graphical desktop session and do not access the user's projects. GitHub Actions is configured to run the platform-independent checks and renderer build on macOS, Windows, and Linux when the repository is hosted on GitHub; this does not validate full desktop workflows on those systems.

## Beginner quick start

On first launch, follow or skip the short introduction. Create a project, choose its production type and script language, and enter its title, logline, synopsis, and creators. Open **Script** and add scenes. A scene has a heading, action, character cue, dialogue, location, duration, and production notes. Visit **Project bible** for character and location references. Under **Production**, add shoot days, assign and order scenes, prepare a call sheet, and manage lighting and sound notes. Use **Script breakdown** to track item owners and status. Use **Breakdown**, **Shotlist**, **Equipment list**, **Shortlists**, and **Tasks** to organize production details. Print the current production view, the complete book, or a single call sheet from the system dialog. Projects save automatically as you work. New installations start without projects.

## Storage, project format, and recovery

New installations store projects under `~/Documents/Takevera/<project-id>.json`; imported images are copied to `~/Documents/Takevera/assets/<project-id>/`. Existing installations keep using `~/Documents/ScriptStudio` when it contains projects, so upgrading does not hide or move existing data; use **Move projects…** to switch it to a `Takevera` folder. In Settings, choose **Move projects…** to select a parent folder; Takevera copies the complete storage folder into a `Takevera` subfolder, verifies the copy with SHA-256 file hashes, updates copied-image references, and switches future saves to the new location. The old folder remains in place as a rollback copy, which also keeps linked images working; remove it manually only after checking the new location. The selected path is saved in the app profile. JSON is UTF-8, human-readable, and intended as the initial open project format. The versioned envelope, full-folder manifest, common scene fields, index-based links, and compatibility rules are documented in [docs/PROJECT_FORMAT.md](docs/PROJECT_FORMAT.md), with a permissive [JSON Schema](docs/project-format.schema.json). A save after more than 30 seconds since the previous save creates a timestamped automatic snapshot. Up to ten automatic snapshots are retained; recovery points remain until you delete them. The backup manager can list, compare two valid snapshots or recovery points by script field, restore, and delete them; corrupt copies cannot be compared. If the main project JSON is missing or damaged, the home screen offers its newest valid backup; restoring keeps the damaged original as a removable quarantined copy. If no valid backup exists, the home screen reports that without modifying project files. From the home screen, use **Export full project folder** to create a `.takevera` folder containing `takevera-project.json` and `assets/`; **Import full project backup** restores it under a new local project ID. The importer verifies each image checksum and copies the images into local project storage. Keep the manifest and assets folder together when moving or copying the backup. Avoid editing a project file while Takevera is open.

## Languages and accessibility

UI strings live in `locales/nl.json` and `locales/en.json`, separate from application code. Interface language is stored in local app settings. Project script language is its own project field. The interface uses native controls and semantic buttons, supports keyboard focus, and can be resized for narrower windows. Controls without an associated label receive an accessible name from their nearby visible label or prompt, including dialogs opened after the main view. Keyboard support includes Cmd/Ctrl+N, Cmd/Ctrl+S, and Cmd/Ctrl+F for project-wide search while a project is open. Undo and redo are available for project edits while the app remains open; named revisions persist with the project. The scene list supports keyboard navigation with the arrow keys and Home/End; focusable scene groups expose their selected state and key shortcuts to assistive technology. Interface scaling can be changed in Settings and is saved as an app preference. Settings also offer a high-contrast theme with stronger borders and visible keyboard focus, plus a preference to hide or show the contextual writing tip and reopen the introduction.

## Privacy and optional future services

Projects and AI credentials are stored locally. On macOS, Takevera keeps app-managed project files, backups, and copied project images readable and writable only by the current user, and restricts the default project folder itself. Project exports written by Takevera, including JSON, FDX sidecars, DOCX, and full `.takevera` folders, are also restricted to the current user. It does not change permissions on a parent folder selected by the user; shared-folder sync follows the permissions of the shared folder selected by the user. The app makes no requests for project data in the background. Moodboard links open only after a click and are limited to HTTP and HTTPS destinations. When spelling is enabled while editing a script on Windows or Linux, Electron may download a missing Hunspell dictionary from its Chromium dictionary CDN; typed words are not sent to Google. Disable spelling in Settings to prevent dictionary downloads. A user-confirmed weather lookup sends only the entered town/postcode and shoot date to Open-Meteo; avoid entering a street address. Weather data are attributed to Open-Meteo under CC BY 4.0. Its free endpoint is for non-commercial use; teams using Takevera commercially must follow Open-Meteo’s current commercial licensing and pricing terms. Forecasts are available up to 16 days ahead; manual weather entry remains available. If the user configures AI and confirms a request, the task-specific context shown in the preview (up to 16,000 characters for full-script tasks) and their instruction are sent to the endpoint they selected; API charges, retention, and provider terms are controlled by that provider. Local model servers can be used without sending text to a cloud provider. Secure key storage depends on Electron platform support. No AI result overwrites source text automatically. Optional shared-folder snapshot sync and optional self-hosted real-time collaboration are available. Snapshot sync writes only after confirmation and does not merge edits at field level. Real-time collaboration uses Yjs for project content and scene comments; configure and host the server yourself. Back up the folder before use.


## Shared-folder sync

Choose a shared directory in **Settings**. Takevera creates a `.scriptstudio-sync` folder there. For a project, click **Sync now** and confirm before data is written. The shared snapshot includes the project JSON and local PNG/JPEG/WebP assets recognized by the project bundle. Sync is manual; it does not watch the directory or merge edits at block level. When both copies changed, choose the shared copy or this Mac's copy. Choosing the shared copy first saves a local recovery backup. New shared projects can be imported from Settings. The selected path is stored in this user's local app settings, so each device must select the shared directory. Snapshot sync has no automatic merge or live presence; cloud drive timing and filesystem locking vary. The production workspace shows whether the local copy is only on this device, still unsynced, changed since the last sync, synchronized, or offline, along with the last successful sync time. This status is local to each device. For simultaneous editing, use the optional self-hosted real-time server described below. Keep independent backups.

## Formats and licensing

The app is MIT licensed. PDF.js is bundled under Apache License 2.0 (see `node_modules/pdfjs-dist/LICENSE`). The app reads and writes its documented JSON project data, imports/exports the project interchange envelope, and imports PNG, JPEG, and WebP images. The interchange envelope is JSON with `format: "scriptstudio-project"`, `formatVersion: 1`, and `project` and `assets` fields. The export embeds PNG, JPEG, and WebP assets, including available linked files, up to 28 MB total; missing or unsupported files are omitted with a warning. For larger image collections, the full `.takevera` folder backup stores asset files separately, with no combined image-size cap (up to 100 images, 15 MB per image); each image is SHA-256 verified on import. PDF import extracts selectable text offline with PDF.js and detects likely scanned pages. On macOS, users may run local Apple Vision OCR for those pages; this requires the Swift command-line tools, recognizes up to 100 scanned pages per import, and sends no PDF data over the network. The preview appears before replacing scenes. PDF layout and original pagination are not preserved. DOCX import reads text and common Word paragraph styles and guesses screenplay scene headings and dialogue cues. Ordinary Word files do not contain Takevera production metadata; script-only import asks before replacement and saves the prior script as a revision. DOCX export asks whether to include an optional hidden custom XML project snapshot; declining exports only the visible script. The snapshot can be imported back as a new project, retaining production data, comments, and revision history while applying the visible DOCX screenplay text. The custom project part may be removed by other word processors. Image files are not embedded in DOCX, and neither direction preserves complex Word layout or native Word tracked-change history. FDX import/export covers basic scene headings, action, character, dialogue, parenthetical and transition paragraphs. It reads and writes FDX revision-set definitions and paragraph revision marks, and maps recognized revision colors to scene print colors. Because those data do not fit the standard script format, export can optionally write a companion `.scriptstudio.json` file; importing the FDX beside that file restores the production project as a new project and applies the FDX script text. The sidecar includes local image references rather than image files, and may include contact details, so it is an explicit opt-in. Without the sidecar, FDX cannot preserve production data, comments, or full historical script snapshots. Complex formatting, inline mixed-run marks, and some FDX variants are not preserved; inspect exports in the target editor before relying on them. Fountain support covers basic scene headings (`INT.`, `EXT.`, `INT./EXT.`, and `EXT./INT.`) and multiple structured character and dialogue blocks per scene. Custom script elements and cues export as plain text. Fountain export omits production notes and production-book data. Import replaces the current scene list and clears scene links in shoot days, shots, shortlists, and storyboards; approved shoot days and scenes must be unlocked first. Celtx import/export is not implemented; no protected or proprietary format is reverse engineered.

## Development and contributions

Run `npm start` for the app. Use Node.js 22.13+ or 24+ for development; the packaged Electron app embeds its own Node runtime. Electron is a development dependency; no runtime service is required for local project work. To use AI, configure an OpenAI-compatible endpoint and model in Settings. Leave the API key blank for a local server that requires no key. Do not expose a local model endpoint to untrusted networks. Realtime collaboration and self-hosted server setup are documented in the sections below. Project-wide continuity assistance includes the selected story bible, characters, locations, and scene continuity in its preview. Translation tasks ask for a target language. AI provider-specific adapters and advanced pagination remain future work. Contributions should keep private/offline storage the default, preserve the documented JSON structure, and make incomplete features visible in the interface.


## Realtime samenwerking (optioneel)

Takevera bewaart projecten standaard lokaal. De instelling voor realtime samenwerking is optioneel en verbindt een project uitsluitend nadat de gebruiker de server en het delen van projectinhoud heeft bevestigd. Vooraf maakt de app een lokale herstelkopie. Projectinhoud en scèneopmerkingen worden als afzonderlijke Yjs CRDT-documenten uitgewisseld; de client bewaart ook een offline IndexedDB-kopie. De server bewaart binaire Yjs-snapshots en gebruikt projectgebonden uitnodigingstokens waarvan alleen hashes op schijf staan.

### Zelf hosten

1. Gebruik Node.js 22 of hoger.
2. Initialiseer servertoegang: `npm run collab:admin -- init ./scriptstudio-collaboration-data`.
3. Maak een projecteigenaar aan: `SCRIPTSTUDIO_COLLAB_DIR=./scriptstudio-collaboration-data npm run collab:admin -- invite <project-id> owner "Naam"`. Project-ID staat in het projectexportbestand.
4. Start de server met dezelfde datamap: `SCRIPTSTUDIO_COLLAB_DIR=./scriptstudio-collaboration-data npm run collab:server`.
5. Start optioneel de webbeheerinterface vanuit een tweede terminal met dezelfde datamap: `SCRIPTSTUDIO_COLLAB_DIR=./scriptstudio-collaboration-data npm run collab:admin:web`. Open `http://127.0.0.1:1235` en voer de tijdelijke token uit de terminal in. De token wordt niet opgeslagen en de interface luistert uitsluitend op localhost. Voor beheer op afstand gebruik je een beveiligde SSH-tunnel.
6. Maak uitnodigingen via de webinterface of CLI. Trek toegang in met `revoke <invite-id>` en bekijk uitnodigingen met `list [project-id]`.
7. Stel in Takevera een `wss://`-adres in voor externe verbindingen. `ws://` is alleen toegestaan voor localhost. Zet een server op afstand achter TLS en een reverse proxy. Hosting, domein en TLS kunnen kosten met zich meebrengen.

De server bindt standaard aan `127.0.0.1:1234`; pas `SCRIPTSTUDIO_COLLAB_HOST` en `SCRIPTSTUDIO_COLLAB_PORT` aan wanneer dat nodig is. Serverbestanden worden opgeslagen in de opgegeven datamap. De optionele beheerinterface bindt alleen aan `127.0.0.1:1235`; pas de poort aan met `SCRIPTSTUDIO_ADMIN_PORT`. Ze biedt serverstatus, auditregels en retentiebeheer. Projectuitnodigingen met rollen kun je ook in Takevera beheren via Instellingen; plak daar de tijdelijke localhost-token uit de terminal. De desktopapp stuurt deze token uitsluitend naar `127.0.0.1` en bewaart hem met macOS Sleutelhanger wanneer beschikbaar. Er zijn geen ingebouwde gebruikersaccounts, TLS-terminatie of automatische back-ups; beheer TLS en serverback-ups zelf. Gebruik `npm run collab:admin -- status` voor een terminaloverzicht, `audit --project <id> --limit <aantal>` voor auditregels en `retention <dagen>` om retentie in te stellen (1–3650 dagen; standaard 90). Een actieve server past een gewijzigde retentie binnen een uur toe. Auditregels registreren toegestane en geweigerde authenticatie, wijzigingen aan samenwerkingsdocumenten, verbroken verbindingen, geweigerde schrijfpogingen en uitnodigingsbeheer. Ze bevatten geen documentinhoud of uitnodigingstokens, worden met beperkte bestandsrechten opgeslagen, ouder dan de ingestelde termijn verwijderd en op maximaal 32 MiB begrensd. Een ingetrokken uitnodiging wordt bij volgende berichten geweigerd. Een al verbonden gebruiker kan nog lokale gegevens hebben die eerder zijn gesynchroniseerd.

De huidige realtime implementatie ondersteunt gelijktijdige project- en scènecommentaarwijzigingen via Yjs. Bij elke opgeslagen wijziging terwijl realtime samenwerking actief is, registreert het project de ingestelde gebruikersnaam, het tijdstip, het type wijziging, gewijzigde scènes en gewijzigde projectruimten. De lijst toont de laatste 30 gebeurtenissen, bewaart maximaal 1.000 en meldt wanneer oudere gebeurtenissen zijn verwijderd. Een wijziging aan één scène kan een begrensd herstelpunt van script-/revisievelden bevatten als aantal en volgorde van scènes gelijk blijven: maximaal 20 punten, samen 1 MiB en maximaal 128 KiB per punt. Vanuit de activiteitenlijst kun je deze velden van vóór de wijziging herstellen; reacties en afbeeldingen blijven behouden. Te grote wijzigingen, scèneverplaatsingen en wijzigingen aan meerdere scènes blijven alleen activiteiten; gebruik daarvoor benoemde revisierondes. Rollen worden server-side afgedwongen voor inhoud en opmerkingen. De app toont actieve namen en laat bij de geopende scène zien wie daar kijkt. Serverbeheer is beschikbaar via de terminal en een tijdelijke token-beveiligde localhost-webinterface; projectuitnodigingen en roltoekenning zijn ook beschikbaar vanuit Takevera. Ingebouwde gebruikersaccounts zijn niet gebouwd. De app schakelt bewerkvelden uit zodra een lezerrol is herkend; reageerders houden alleen scèneopmerkingen over. De server blijft de uiteindelijke autoriteit en weigert schrijfacties buiten de rol.

## Huidige scope en beperkingen

De app is een werkende lokale desktopbasis en bevat script- en productieonderdelen, scene-breakdown, shotlists/shortlists, borden met verplaatsbare en schaalbare items, storyboardkaarten met print/PDF-uitvoer, call-sheet-print, lokale back-ups, gedeelde-map-snapshotuitwisseling, AI via een configureerbaar compatibel endpoint en de optionele samenwerkingsserver. De voorlopige scèneplanning kan dagscènes ordenen op locatie, cast, beschikbaarheid, productiebehoefte of scriptvolgorde, start op de calltime en vraagt per scène een aparte draaitijd; ze markeert bekende of onbekende cast- en locatiebeschikbaarheid en meldt scènes waarvan de locatie niet aan een projectbijbellocatie gekoppeld is. Voor verplaatsingen vraagt ze een standaard reistijd in minuten wanneer een bestemming geen eigen schatting heeft; een numerieke reistijd in de projectbijbel van de bestemmingslocatie overschrijft die standaard. Als elke verplaatsing een eigen schatting heeft, mag de standaard leeg blijven. Reistijd wordt tussen locatieblokken ingevoegd. Gebruikers kunnen vóór elke scène een voorbereidingsbuffer instellen; een dag eindigend binnen 15 minuten voor de wrap krijgt een waarschuwing. Als een pauzetijd is ingesteld, vraagt de planner om de pauzeduur en plant die na de lopende activiteit op of na de ingestelde tijd. De planner berekent geen route, locatiespecifieke opbouwtijd of optimale castcombinatie. Controleer de planning en vul ontbrekende productietijd in voordat je die deelt of definitief maakt. De selectie aan exportonderdelen is als projectsjabloon op te slaan. Print het volledige draaiboek of alleen de actieve draaidag; exports tonen versienummer, status en datum. Shotlist, lichtplan, geluidsplan en cast-/crewlijst kunnen daarnaast afzonderlijk als printvriendelijk PDF-document worden opgeslagen; telefoonnummers vereisen zowel exporttoestemming als toestemming per persoon. De lokale distributie is ad-hoc ondertekend, maar niet met een Apple Developer ID en niet door Apple genotariseerd. macOS is het huidige doel; Windows- en Linux-builds zijn niet gevalideerd.

Niet alle eisen uit de oorspronkelijke productspecificatie zijn geïmplementeerd. De samenwerkingsactiviteitenlijst bewaart maximaal 1.000 gebeurtenissen; begrensde herstelpunten zijn beschikbaar voor een wijziging aan één scène als de scènestructuur gelijk blijft. Te grote wijzigingen, scèneverplaatsingen en wijzigingen aan meerdere scènes vereisen een benoemde revisieronde. Undo/redo geldt alleen tijdens de huidige sessie. Bij een binnenkomende samenwerkingswijziging wordt de undo/redo-sessiegeschiedenis met een melding gereset om overschrijven van nieuwere inhoud te voorkomen. FDX/DOCX kunnen alleen extra Takevera-productiegegevens herstellen wanneer die door Takevera zelf zijn ingesloten (DOCX) of als begeleidend JSON-bestand zijn meegeleverd (FDX); gewone bestanden bevatten alleen de herkende scriptstructuur. Celtx-import, een ingebouwde lokale model-runtime, een updatekanaal en ingebouwde gebruikersaccounts ontbreken. Rollen worden beheerd met projectgebonden uitnodigingen via Takevera, de CLI of de localhost-beheerinterface. De app biedt een begrippenlijst en begint zonder projecten. PDF-import extraheert selecteerbare tekst en kan op macOS maximaal 100 scans lokaal herkennen met Apple Vision; daarvoor zijn de Swift-opdrachtregeltools vereist. De PDF-opmaak en paginering blijven niet behouden. AI werkt alleen met een compatibel chat-completions-endpoint; een lokaal model moet de gebruiker apart installeren en starten. Een productieboek kan in zijn geheel of per actieve draaidag worden afgedrukt en toont het ingestelde versienummer en de status. Moodboards kunnen afzonderlijk als printvriendelijke PDF worden opgeslagen. AI-invoer wordt alleen verstuurd na de AI-actie en keuze van endpoint/provider.

De projectbestanden zijn JSON en kunnen via de projectexport worden verplaatst. Lokale automatische back-ups zijn beschikbaar vanuit projectbeheer. Verwijdering van een project verwijdert de projectbestanden en bijbehorende lokale back-ups volgens de appflow.
